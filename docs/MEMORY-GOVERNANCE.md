# 三层记忆治理规范

> 本文件定义三层记忆的**职责、去重、晋升、冲突、生命周期、来源与主体、缓存与修正语义**。
> 所有规则都是可判定的；无法判定的判断交给模型，由插件执行结果。

---

## 一、职责边界

三层不是"重要程度"分层，而是**适用范围**分层。判据只有一条：**这条经验能否脱离产生它的上下文被复述和使用。**

| 层 | 职责 | 判定问题 | 反例（不该放这层） |
|---|---|---|---|
| `global` | 跨任务工作方法 | 「不指名任何文件/项目/会话，还能说清楚吗？」 | 「修 cart.ts 先看耦合」——指名了文件 |
| `session` | 当前会话的背景与约束 | 「换个会话还有意义吗？」 | 「npx 前先查 .bin」——任何会话都成立 |
| `reflection` | 单个任务的观察与教训 | 「它描述的是一次任务，还是一类任务？」 | 「遇到别名 bug 先写 === 探针」——已是一类做法，应晋升 |

**边界冲突的裁决顺序**

1. 能脱离上下文复述 → `global`
2. 不能脱离，但描述的是**约束/背景**（"A 与 B 耦合"）→ `session`
3. 不能脱离，且描述的是**一次任务的现象**（"改 A 导致 B 失效"）→ `reflection`

> 第 2 与第 3 的区别：约束是**改之前就要知道的**，观察是**做完之后才得到的**。

## 二、去重与晋升

### 2.1 写入四分类（模型判断，插件执行）

`task_reflect` 的每条 lesson 必须声明与已有记忆的关系：

| 分类 | 含义 | 插件动作 |
|---|---|---|
| `new` | 之前没有这条经验 | 追加新条目 |
| `repeat` | 同一经验再次出现 | **不新增**，原条目 `hits += 1`，刷新 `last_seen` |
| `revise` | 同一经验被修正 | 旧条目置 `superseded`，写新 `revision` |
| `none` | 无新增信息（泛泛而谈） | **不记录** |

判定依据是语义，不是字符串。插件不猜，只执行模型给出的分类。

> 不声明就等于默认 `new`，反思里会堆积大量近似重复，
> 而这些重复会按条数占用注入预算。

### 2.2 晋升 = 状态迁移，不是复制

三个概念必须分开，不能用一个字段兼职：

| 概念 | 回答 | 落点 |
|---|---|---|
| `source` | 经验最初从哪产生 | 条目上的 `source{task_id, session_id, workspace, at}` |
| `promoted` | 这条是从更底层晋升上来的产物 | 派生条目上的 `promoted_from:<源 lesson_id>` |
| `active` | 当前是否仍参与注入 | 读取时计算，不是存储状态 |

**源条目不被删除。** 它是经验的来源与历史依据，只是**不再作为有效记忆注入**。

**停用只作用于「被派生条目覆盖的那条注入路径」。**

一条来源可能被多个层级引用。若简单地把源记录标记为失效，会误伤仍然有效的引用。
因此规则是**按路径判定**：

> 对当前注入路径 P，来源条目 R 停用，当且仅当存在一个 `promoted_from === R.id`
> 的派生条目 D，且 **D 在路径 P 上可见**。

由此得到的行为：

| 晋升目标 | 源会话 | 目标会话 | 其它会话 |
|---|---|---|---|
| `global`（处处可见） | 用派生条目 | 用派生条目 | 用派生条目 |
| `session:S2`（仅 S2） | **仍用源条目**（不误伤） | 用派生条目 | 仍用源条目 |

`promote` 只写派生条目与 `promoted_from`，**不修改、不删除源记录**；
源条目的停用是读取时按上述规则算出来的，所以：
- 关掉某一层（对照实验）时，覆盖它的派生条目不可见 → 源条目自动恢复生效
- 审计时永远能看到「这条全局方法是从哪个任务的哪条反思来的」

> 已实现并被 8 条回归测试覆盖（`selftest-lessons.mjs` → "晋升 = 状态迁移"）。

## 三、冲突处理

冲突指**两条生效记忆对同一行为给出相反要求**。

### 3.1 优先级（从高到低）

| 序 | 规则 |
|---|---|
| 1 | **具体性优先**：`session` > `global`。本会话的约束覆盖通用方法 |
| 2 | **同层同类**：`revision` 高者生效；同 revision 不可能同时生效（见 5） |
| 3 | **同层跨 kind**：`directive` > `lesson`。明确方法覆盖经验建议 |
| 4 | **用户显式否定**：任何一条被用户直接否定的记忆立即 `deprecated`，不参与优先级比较 |

### 3.2 呈现义务

插件**不得静默取舍**。检测到冲突时，注入材料里必须并列两条并标明冲突：

```
[CONFLICT] 以下两条对同一行为给出不同要求，按「具体性优先」以 Session 那条为准：
  - global: 改完代码先跑测试
  - session: 本项目测试脚本当前损坏，改完先人工核对
```

> 静默取舍会让模型在遇到反例时无法纠正，也无法把冲突反馈回来。

## 四、生命周期

每层独立状态机，状态随条目持久化：

```
                 revise                delete
  active ────────────────► superseded ──────► deleted(墓碑)
    │                          ▲
    │ deprecate                │ promote
    ▼                          │
  deprecated ──────────────────┘
```

| 状态 | 含义 | 是否注入 |
|---|---|---|
| `active` | 生效 | ✅（且未被可见派生条目覆盖） |
| `superseded` | 被新 revision 取代 | ❌ |
| `deprecated` | 显式失效（条件不再成立/被用户否定） | ❌ |
| `deleted` | 墓碑 | ❌ |
| 被晋升覆盖 | 有可见的派生条目替代它 | ❌（**源记录保留**，只是在该路径不注入） |

**各层特有的转换**

| 层 | 允许的转换 |
|---|---|
| `reflection` | active → superseded / promoted / deprecated / deleted |
| `session` | active → superseded / deprecated / deleted（**不可**晋升，会话背景没有跨会话意义） |
| `global` | active → superseded / deprecated / deleted（**只能**从 reflection 晋升而来） |

## 五、修正语义：旧内容不得继续生效

两条独立保证，缺一不可：

1. **写入侧**：`revise` 必须同时产生「新 revision」和「旧条目 superseded」两个事实，不能只写新的。
2. **读取侧**：渲染时按 `lesson_id` 取**最高 revision 的 active 条目**，其余一律丢弃。

> 只做写入侧不够：任何读取路径（注入、CLI list、导出）都必须经过同一个解析函数，
> 否则某条旁路就会把旧文本带出来。

**必须断言的事实**：修正后，旧文本在整个 system prompt 中**零出现**。

## 六、来源与适用主体

两个独立维度，不能混用：

| 维度 | 字段 | 回答的问题 | 示例 |
|---|---|---|---|
| **来源** `source` | `task_id` / `session_id` / `workspace` / `at` | 这条记忆**从哪来** | 来自 `task-3f2a`，在会话 S1，工作区 `D:\proj` |
| **主体** `subject` | `kind` + `id` | 这条记忆**对谁有效** | `global`（所有人）/ `session:S1` / `workspace:D:\proj` |

**为什么必须分开**

- 晋升时：来源不变（还是那个任务），主体改变（session → global）
- 跨会话复现时：来源增加（新 task_id），主体不变
- 审计时：能回答"这条全局方法，最初来自哪个任务"

**当前实现的缺口**：只有 `task_id` 和 `session_id`，二者被当作同一件事用。
`subject` 由 `scope` 隐式表达，`workspace` 完全缺失。

## 七、缓存行为（已实测，按层）

`## Accumulated Lessons` 是一个**整体 section**：任何一层的任何变更都会改变该段文本，
因此都会触发一次**全量提示词重算**（见 `LESSONS-INJECTION.md` 第五节）。

| 变更层 | 是否改变 section | 是否全量重算 | 实测 |
|---|---|---|---|
| `global` 新增/修正 | 是 | 是 | 待补 |
| `session` 新增/修正 | 是（仅本会话生效，但文本变了） | 是 | 待补 |
| `reflection` 新增/修正 | 是 | 是 | ✅ 已测：单条修改 → `cached=0`，下一次恢复 |

**结论（当前设计的固有限制）**：不存在"只让某一层失效"的做法，
除非把三层拆成**三个独立 section**。拆分的收益是缓存局部性，代价是段落数量增加。

## 一之二、语义边界的判定分工

三层目前还是**存储分类**，不是严格的语义分类：把一条具体修复经验写进 global，
程序照样接受。修边界不能靠硬编码规则（"含文件名的就降级"这类），那会把模型的
语义判断换成脆弱的关键词匹配。

**分工**

| 谁 | 负责 | 依据 |
|---|---|---|
| 模型 | 判断「这条内容属于哪一层」「够不够抽象」 | 语义 |
| 程序 | 校验结构、状态、引用关系 | 客观事实 |

**程序做三件事**（inspectMemoryGraph）

1. **引用完整性**：conflicts.with / promoted_from 是否指向存在的条目 → 悬空则 `warn`
2. **状态一致性**：scope 与 subject / session_id 是否自洽 → 不自洽则 `error`
   - global 的 subject.kind 必须是 global
   - session / reflection 必须有 session_id
3. **声明完整性**：非 reflection 层必须写 boundary（为什么属于该层）→ 缺失则 `warn`

**程序明确不做**

- 不判断内容粒度（"这条太具体了不该进 global"）
- 不判断抽象程度
- 不拦截写入（除结构不一致外）

`boundary` 字段是可审计的边界声明：模型必须写，但写什么由它决定。
程序只保证它存在，从而让"边界是否逐渐失控"变成可复查的问题。

检查入口：`node tools/lessons.mjs check`
